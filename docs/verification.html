Verification and hashes

How PI-Backuper knows a copy is good, and what's in the .hash.txt file.

Two different checks

There are two separate questions, and the app answers both.

  1. Is the image file still intact? That's what the .hash.txt is for. It's written at backup time and checked at every restore, no matter what the verify option is set to.
  2. Did the destination actually keep what was written? That's Verify after writing. Everything written is read back and hashed again.

Verify after writing

SD cards fail quietly. A worn-out card can accept writes and hand back different data later. A fake card that says 128 GB but really holds 16 GB will happily take writes past its real size and throw them away. Neither tells Windows anything is wrong. The only way to know is to read it back.

JobWhat's read backCompared with
BackupThe new image file, decompressedThe hash of what came off the card
RestoreThe card, for the length of the imageThe hash of the image
CloneAll of card B, for the size of AThe hash of card A

It roughly doubles the time of a restore or clone, since reading the card is about as slow as writing it. Turn it off when you're in a hurry and trust the card. For anything you care about, leave it on.

If verify fails on a restore or clone you'll see "Read-back check failed: the device didn't keep what was written. The card may be worn out or fake." Try another card. If it fails on a backup, the problem is the drive you're saving to.

The .hash.txt file

Every backup gets a sidecar file named after the image with .hash.txt on the end. It's one line of plain text:

sha256 31914983424 9f2c4e...e81b
  • The hash algorithm. New backups always use sha256.
  • The size in bytes of the uncompressed image, which is the size of the card it came from.
  • The hex digest of the uncompressed image.

The hash is always of the raw disk contents, never the .gz file. So you can decompress or recompress an image yourself and the hash file still applies.

The size matters for gzip images. Gzip can only record sizes up to 4 GiB, so for bigger cards the hash file is the only place the real size is kept. That's how restore knows up front whether an image will fit.

Checking a hash by hand

For a plain .img, in PowerShell:

Get-FileHash .\pihole.img -Algorithm SHA256

For an .img.gz you have to hash the decompressed data. On Linux or WSL:

gunzip -c pihole.img.gz | sha256sum

Compare the result with the last field in the .hash.txt. Windows prints it in upper case; that doesn't matter.

Older backups (1.0.x)

Version 1.0.x used the same one-line format, and some of those files say md5 instead of sha256. Those still work. When restoring, the app uses whatever algorithm the file names, both for checking the image and for the read-back.

A hash file that's missing or can't be read is treated as "no hash file". The restore goes ahead and the confirmation dialog tells you the image can't be checked.

How a backup's files are written

  1. The image goes to name.img.gz.partial.
  2. When it's finished it's flushed to disk and, with verify on, read back and checked.
  3. Any old .hash.txt with the same name is deleted.
  4. The .partial file is renamed to its real name.
  5. The new .hash.txt is written (also via a temporary file and a rename).

So at no point is there a finished-looking image with a half-written or stale hash file next to it.
