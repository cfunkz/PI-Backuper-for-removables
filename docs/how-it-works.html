How it works

A tour of the code for anyone who wants to change it, or just wants to know what it's doing to their card.

The code is split into three layers that only talk downwards:

gui.py      the window; runs jobs on a worker thread
  │
  ├── windisk.py   Windows: list disks, open them raw, lock volumes
  └── imaging.py   backup / restore / clone / verify, pure Python

imaging.py never imports anything Windows-specific. It works on any object that looks like a disk, which is why the tests can run on Linux with fake disks in memory.

imaging.py

The device interface

Anything with these is a device:

MemberMeaning
sizeTotal size in bytes.
sectorSector size, usually 512 or 4096.
read(offset, length)Read bytes. Offsets and lengths are whole sectors.
write(offset, data)Write bytes. Same rule.
flush()Make sure writes have reached the device.

Jobs

FunctionWhat it does
backup(dev, out_path, job, compress=True, verify=True)Images the whole device to out_path via a .partial file, writes the .hash.txt, returns the SHA-256.
restore(image_path, dev, job, verify=True)Writes a plain or gzip image from sector 0, checks it against the hash file, writes the first block last.
clone(src, dst, job, verify=True)Copies src onto dst the same way.

Each raises Cancelled if the job was cancelled, VerifyError if a hash check fails, ValueError for size problems, and lets OSError from the device through.

Job

Job is a small object shared between the GUI and the worker. It holds a cancel flag (job.cancel(), checked with job.check()) and a progress callback, on_progress(phase, bytes_done, fraction). Progress calls are throttled to four a second so the GUI isn't flooded.

The copy loop

pump() moves data in 4 MiB chunks. A reader thread pulls chunks from the source and puts them on a queue up to 8 deep (32 MiB). The main worker thread takes them off and writes them. So the source is being read while the target is being written, and the job runs at the speed of the slower device instead of the sum of both.

Hashing happens on the reader side and gzip on the writer side. Both release Python's GIL on big buffers, so they run in parallel too. If either side fails, both stop and the first error is raised.

Writing the first block last

Restore and clone read the first 4 MiB, write zeros there, copy everything else, and only then write the real first 4 MiB. See No half-restored cards.

Partial sectors

A raw disk only accepts whole sectors, but a gzip image doesn't have to end on a sector boundary. write_any() writes the whole sectors directly, then reads the last sector from the device, overlays the leftover bytes and writes it back. Bytes past the end of the image are left as they were.

Hash file helpers

read_sidecar() returns (algo, size, digest) or None if the file is missing or unreadable. write_sidecar() writes through a temp file and a rename. image_size() gives the uncompressed size: the file size for plain images, the hash file's size for gzip ones, or None if it can't know.

windisk.py

gui.py

A single Tkinter window. When you start a job it does all the checks on the main thread (so it can show dialogs), then runs the work on a background thread inside keep_awake(), the volume locks and the open disks, in that order.

The worker never touches Tkinter directly. It puts messages on a queue (progress, note, done, error) and the window picks them up ten times a second. Speed and time-left are worked out from the last four seconds of progress, and reset whenever the phase changes (say from Writing to Verifying).

All inputs are disabled while a job runs, so you can't start a second one or change the settings mid-job.
