Restore

Write an image file back onto a card. This erases the card.

Restore wipes everything on the target device. Double-check the disk number, size and drive letters in the confirmation dialog before you click Yes.

Steps

  1. Choose the target card under Device.
  2. Click Open image… and pick an .img or .img.gz file.
  3. Click Start restore.
  4. Read the confirmation carefully. It names the exact disk that will be erased. The default button is No.
  5. Wait for "Restore complete and verified. Safe to remove the device."

Progress shows Writing and then, if verify is on, Verifying.

What images work

  • Backups made by any version of PI-Backuper, including old ones with MD5 hash files.
  • Plain .img files from anywhere, such as an OS image you downloaded.
  • Gzipped images (.img.gz). The app checks the file's first bytes, not the extension, so a gzip file with a different name still works.

Other formats like .xz, .zip or .7z aren't supported. Unpack them to a plain .img first.

With and without a .hash.txt

If the image has its .hash.txt beside it, the image is hashed while it's being written. If the result doesn't match the file, the restore stops with "The image doesn't match its .hash.txt file, so it's damaged" and the card is left blank. The real partition table is never written, so nothing tries to boot from a broken copy.

If there's no .hash.txt, the confirmation dialog says so. The restore still works and verify still reads the card back to check it kept what was written. It just can't tell if the image file itself was damaged before you started.

Card sizes

The target must be at least as big as the image. Two "32 GB" cards from different brands are rarely exactly the same size, so an image from one may be a few megabytes too big for another. If the size is known up front (plain image, or gzip with a .hash.txt) it's checked before anything is written. For a gzip image with no hash file the size isn't known in advance, so the restore stops when it hits the end of the card and the card is left blank.

Restoring onto a bigger card is fine. The extra space is left alone. On a Pi you can grow the root partition afterwards with sudo raspi-config → Advanced Options → Expand Filesystem.

What happens on the card

  1. All of the card's volumes are locked and dismounted. If one can't be locked, the restore doesn't start (see Couldn't lock).
  2. The first 4 MiB of the card (partition table and boot area) is overwritten with zeros.
  3. The rest of the image is written.
  4. The image's hash is checked against the .hash.txt, if there is one.
  5. The real first 4 MiB is written last, and everything is flushed.
  6. With verify on, the whole written area is read back and hashed.
  7. Windows is told to re-read the partition table, so the new partitions show up.

Because the start of the card is written last, a restore that gets cancelled, fails or loses power leaves a card that Windows sees as blank. You get a clear message saying so: "The device is now blank or only partly written. Run the restore or clone again before using it."

After restoring

Windows may pop up "You need to format the disk in drive X" for the Linux partition. Click Cancel. Formatting it would wipe what you just restored.
